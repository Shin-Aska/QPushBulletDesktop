# Consistent UI verification

The final frozen application passed independent verification on 14 November 2026. The [exact verification report](../.runtime/consistent-ui/final-verification.md) and [machine-readable evidence](../.runtime/consistent-ui/final-verification.json) retain commands, environment overrides, logs, test results and hashes. The [current fictional UI gallery](../design/ui-review/consistent-ui/index.html) contains the inspected production-widget captures.

- **207 full-suite tests passed** in 13.65 seconds, including the installed Firefox integration test with external requests blocked.
- **106 focused desktop tests passed** in 6.74 seconds. Both runs had zero failures, errors or skips.
- **33 native Qt captures** were inspected across System, Dark, representative Light, and 850×540 layouts. An independent design review also approved 11 representative final images.

The final visual checks confirmed readable selected notification badges, complete Activity Kind pills and Devices Supported pills, consistent reading panes/dialogs, wrapped long notification URLs and vertically accessible final supplied lines. Narrow device tables retain native horizontal scrolling for the final capability column. Notification metadata stays on one line: its row remained 23px high and the list began at y=258 across normal, refreshing and error states at 850px. The fixed 154px header status did not shift the header or body.

Appearance now follows the effective palette across the sidebar, notifications, SMS, devices, activity and review dialogs. **Settings → Appearance** defaults to **System**, which uses the palette/style delivered by Qt and KDE integration where installed. **Light** and **Dark** apply immediately. The preference persists locally as `ui-preferences.json` in the configured `PBDESK_STATE_DIR`, separate from account storage and global desktop settings. Tests covered persistence, releasing explicit overrides when returning to System, and application-palette updates without losing drafts, selections or synchronization state.

Ordinary reconnect/refresh presentation waits three seconds and promotes sustained states even without another snapshot. Core, credential, rate-limit and actionable decryption/backlog states appear immediately. Clickable and keyboard-accessible status details distinguish the local core, provider stream, retained push synchronization and timestamp, and incoming encryption/key readiness. Partial snapshots preserve known fields; account changes clear stale state; core failure overrides previously connected capabilities. **Live updates** describes the stream, not a complete history backup.

Notifications retain the full supplied title/body/newlines and original Copy text, within the existing 65,536-character normalization limit per string. Titles and provider markup remain literal. Complete body and top-level HTTP(S) links require explicit activation, unsafe or visibly shortened URLs stay text, long URLs wrap, and resource loading is disabled. Browser-opening tests used a mocked opener. Pushbullet's [mirrored-notification API](https://docs.pushbullet.com/#mirrored-notifications) describes notification title/body fields; it does not promise full source-app content or a required URL. Omitted source text cannot be recovered. The shortened fictional fixture verifies presentation and does not establish the upstream cause of any user's incomplete notification.

Accepted SMS request cards remain absent from the conversation and retained in Message activity. Review closes only for acceptance matching its exact approved revision and fingerprint. Failed, uncertain and historical actions do not trigger that close. The send/approval pipeline and provider behavior were outside this presentation change.

Verification used private Xvfb/xcb displays and fresh temporary application/state directories. No installation, existing user window, shared core restart, live account, wallet, user database, provider send or device mutation was exercised. The runtime used native **Fusion** with a Qt-delivered dark/magenta System palette; only **Windows** and **Fusion** style keys were available. Actual KDE/Breeze integration remains untested here.
